# WakaTime

Server and frontend plugin. It runs `wakatime-cli` on the bb server host and sends WakaTime heartbeats for the user's activity in a focused bb window, for agent run time (a thread that is active and not waiting: a machine-not-ready display status, or a pending interaction with a turn id), and for the files agents edit or read, all tagged with the bb project, thread, and branch. It uses only bb's own data, so every provider is treated the same; it parses no transcripts and runs no `--sync-ai-activity`.

## How it works

- `server.ts` registers the settings, the `heartbeat` and `status` RPC methods, and the thread lifecycle listeners (`thread.active`, `thread.idle`, `thread.failed`, `thread.archived`, `thread.deleted`, `experimental_thread.events`). Everything is registered first; the host version (for the `--plugin` editor string, `bb/unknown` until it answers) is read once in the background with a 5 s abort. At startup it checks `excludeProjects`, and starts timers for running threads (`threads.listRunning`, each confirmed active with `threads.get`). Disposing the plugin also disposes the runner.
- `src/cli.ts` is the runner. `exec` is injected (default `execFile`, no shell; a job can carry stdin, written newline-terminated, with an error handler so a process that exits early cannot crash the server). It checks the CLI path (absolute, regular, executable; re-checked after a spawn error), allows 4 processes at once and one per key, replaces a waiting job for a key in place, and applies a 150 s timeout. wakatime-cli leaves stderr empty, so failures are classified from the exit code alone (104 `auth`, 102/112 `network`, 103 `config`, spawn error `missing-cli`, kill `timeout`, else `other`) and logged at most once per kind every 10 minutes, never with argv or paths, and with the cli path only as typed. `verify()` re-runs the path check so the status reflects the current `cliPath`.
- `src/heartbeat.ts` holds the pure parts: the argv builder, entity and exclusion rules, the 120 s throttle, a TTL cache for each environment's branch and folder, and context resolution through `bb.sdk`.
- `src/tracker.ts` holds the agent timers. A tick re-reads the thread and sends only if it is still `active` and its own timer is still the registered one, and only if the thread is not waiting (machine-not-ready display status, or a pending interaction with a turn id). `experimental_thread.events` pulls a timed thread's new events, or starts a missing timer after the same live check. A thread skipped because tracking is off or its project is excluded is remembered until it is activated, stops, or settings change, so a stream of payloads does not re-read it. Every submission under `heartbeat:<threadId>` goes through the file pipeline, so a key has one submitter.
- `src/waiting.ts` holds the wait check: true while the machine is not ready or an interaction holds the turn; a failed read counts as not waiting and is logged by error name, once until a read succeeds again.
- `src/excludes.ts` holds the `excludeProjects` diagnostics: it warns once per distinct `excludeProjects` value, by entry position only, and feeds the status panel's unmatched list. The exclusion rule itself stays in `tracker.ts` and `heartbeat.ts`.
- `src/file-activity.ts` does small filesystem checks (`realpath`, `stat`, `lstat`) and otherwise only computes: it counts diff lines, turns completed `fileChange` and `fileRead` items into file specs, keeps only paths inside the environment folder (symlinks resolved, by path segment, no `node_modules` or `.git`), decides `is_unsaved_entity`, and builds the `--extra-heartbeats` objects (exactly a fixed key set, never a diff).
- `src/file-delivery.ts` is the per-thread pipeline: a state seeded at the tip of the thread's event log, a pull that is never queued more than one deep (one running, one waiting; each `events.list` bounded by a 30 s abort, and a pull whose payload sequence is not past what was read is skipped; a failed environment lookup throws so the read position does not move), a buffer capped at 2000 with a per-path read throttle, and a flush with at most one in flight per thread. A tick that finds a flush in flight submits nothing. A job that carries files has a `guard` the runner asks just before spawning, so a send that waited re-checks the settings (nothing the current mode would filter, such as reads after a switch to `edits`) and that no file turned into an existing non-regular entry (a deleted file does not refuse); a refusal puts the chunk back in the buffer, and the next flush drops what the settings no longer allow (counted as filtered) and sends the rest. Each chunk is `lstat`ed at send time; a file that is no longer a regular file goes out as unsaved. An unknown `fileActivity` value means off. Privacy settings are applied on every settings change, pull and flush; when file activity stops for a thread its file state is reset (counted as dropped), and when the thread is no longer timed the state is deleted once no flush is in flight. An outcome of `skipped` or `superseded` puts the batch back (unless the state was reset meanwhile), `failed` counts it. The final stop waits for the flush in flight, then sends every chunk, and stops at the first chunk the runner does not accept.
- `src/activity.ts` turns keyboard, pointer, and wheel input into heartbeat requests while the window is focused and visible. `app.tsx` mounts it as an app overlay (`experimental_appOverlay`) and adds a status section to Settings. Activity just before a route change is credited to the new view.

## What leaves the machine

Per thread: project name, entity (thread title or id), branch, category, time. Per file (when `fileActivity` is on and the entity is the title): the absolute file path on the bb server host, only inside the environment folder, write or read, changed-line count for edits, time; for local files `wakatime-cli` also derives line counts and dependencies. The editor string goes in the User-Agent header. File contents never leave the machine; file names do. The API key stays in `~/.wakatime.cfg`; the plugin never passes `--key`.

## Notes

- Settings are read fresh on every use; nothing is captured in the factory.
- The agent and user categories are selects over the CLI's categories minus `ai coding`, which wakatime-cli v2.27.5 silently drops from external submitters.
- An excluded project sends no bb heartbeats and no file entries.
- Pending file entries live only in memory until the thread's next tick or turn; they are discarded on archive, delete, dispose and reload.
- Per-thread timer state is deleted on idle, failure, archive, delete, and dispose; the file state is kept across idle and freed on archive, delete and dispose (or when the thread stops being timed).
